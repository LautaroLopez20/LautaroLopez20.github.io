Armazon

Como esta armado

Cuatro HTML que comparten CSS. Un solo main.js para el home y el juego, un register.js aparte para el formulario.

Orden de carga

  1. El HTML trae el esqueleto: header, section, footer. Ya se ve algo sin CSS.
  2. Los CSS llegan por <link> y pintan el modo oscuro. Por eso el sitio "anda en negro" desde el primer frame.
  3. main.js se ejecuta y engancha sus addEventListener a DOMContentLoaded.
  4. init() primero muestra el loading, despues abre los menus, y recien al final hace el fetch de la API.

Por que el loading va primero. startLoading() es la primera llamada de init() y el await fetch esta mas abajo. Si el loading arrancara despues, se veria el home vacio durante la espera.

Que carga cada pagina

El mapa de archivos

El flujo del dato

API  ─┬─►  buildHero(games)      4 slides por rating
                 │
                 ├─►  buildCategories(games)  ─┬─► selectGames()      core + relleno, 14 cards
                 │                             ├─► marcarPremium()    corona, precio, carrito
                 │                             └─► initCategoryCarousel()  flechas + dots
                 │
                 └─►  si falla: wireFallbackCarousels()  deja las cards placeholder del HTML

El fallback existe por una razon concreta. Abri Index.html con doble click y la fetch a la API puede fallar por CORS o por no tener internet. Sin wireFallbackCarousels() el home queda con carruseles muertos.

Por que el codigo va embebido aca

Esta pagina se abre con file://. Ahi fetch() no puede leer archivos locales, asi que el codigo real va serializado dentro de estudio/fuentes.js, que se carga como script normal. estudio/build.js genera ese archivo; el boton Recargar codigo lo sobreescribe en memoria con el archivo que elijas del disco.

Contra el enunciado

Requisitos del enunciado

La lista de Requisitos de TPE.txt y donde esta resuelto cada punto. Los tags te saltan a la linea del archivo que lo cumple; el archivo exacto y la linea estan en el tooltip del mouse.

  • HTML5 + JS + CSS3, sin frameworks. Ni Angular ni React ni Bootstrap. Hecho: no hay ni una dependencia en el proyecto.
  • Las 3 paginas del TP1, navegables. Home con destacados y ficha de juego, login, registro.
  • Loading simulado de 5 s, sin GIF, con % y animacion. Tres cuadrados con @keyframes propios y barra que sube por tiempo, no por pasos.
  • Galeria o carrusel con transicion animada. El hero no "se desplaza": entra con transform: translateX() sobre un track, y el salto se dispara por JavaScript con Web Animations.
  • Tres hovers distintos, y el hamburguesa no cuenta. Hay varios: card del juego (home.css:285), panel del usuario y del menu (navbar.css:139 y 373), botones .btnPrimary y .btnSecondary (atoms.css:34 y 64), y los botones del juego.
  • Animacion cuando el registro es correcto. La tarjeta toma .exito y el register.css hace entrar el anillo y el tilde.
  • Datos reales, nada de Lorem Ipsum. Los nombres y las imágenes salen de la API; el fixture del laboratorio son 30 juegos reales.
  • Si hay mas de un juego, imagenes diferentes. Cada card usa su background_image_low_res; si falta, cae a background_image.
  • Titulos reales y de distinta longitud. Vienen de la API, asi que se mezclan nombres de 2 palabras con titulos largos. El enunciado lo pide a proposito.
  • Imagenes de colores variados. Por eso el fondo del hero tiene una capa linear-gradient encima de la foto: el titulo se lee siempre.
  • Mobile first en el home. home.css y navbar.css parten de la version mobile y suben en @media (min-width: 780px).
  • El resto de las paginas, desktop. Login y registro no tienen media queries: se maquetaron para pantalla grande, como pide la aclaracion.
  • Entrega en el branch gh-pages. Falta El repo esta en git-pages. Hay que renombrar la rama antes de subir.

Fecha limite. 30/09/2026 23:59:59. Y el enunciado pide todas las correcciones del TPE1 aplicadas: si algo se toco despues, hay que parados.

Registro

El unico lugar con logica de formulario: 7 campos, un captcha que no se valida y la animacion de exito.

  1. initRegister() engancha el click de Finalizar y los listeners de escritura.
  2. Los listeners de input van una sola vez, adentro de initRegister. Si fueran por click, el segundo click duplicaria listeners.
  3. validarCampos() recorre CAMPOS, marca los vacios con .error y cuelga un <span class="inputError"> adentro del .field.
  4. Las contrasenas se comparan solo si no falta ningun campo.
  5. showRegisterSuccess() agrega .exito a la tarjeta.

El captcha esta fuera a proposito. No es un input de texto, es un checkbox, y el aviso .inputError esta pensado para colgarlo debajo de un campo. Si lo metiera en CAMPOS, el aviso no tendria donde ir.

Laboratorio 1

Loading de 5 segundos

El startLoading() real corriendo con el loading.css real. Los tres cuadrados entran desde izquierda, arriba y derecha.

Lo que hay que mirar. El porcentaje no depende de la API: avanza por tiempo con un setInterval de 50 ms. Por eso siempre dura lo mismo aunque la API responda en 200 ms. Si se quisiera atar a la carga real, habria que mover el .finally.

Laboratorio 2

Hero carrusel

buildHero() real con el CSS real. El track tiene copias decorativas para poder dar la vuelta sin salto.

La vuelta infinita. Se agregan HERO_SLIDES + 4 nodos al track. Los dos primeros y los dos ultimos son copias con .heroGameCopy; cuando el indice pasa el centro se salta el salto. Probá bajar HERO_SLIDES a 1 y mirá como se rompe el calculo.

Laboratorio 3

Paginado del carrusel de categorias

initCategoryCarousel() real. El viewport es fluido con scroll-snap, y una "pagina" es lo que entra en pantalla.

El truco esta en computeLayout(). Divide el ancho del viewport por el paso de card (offsetWidth + 4), redondea, y con eso calcula cuantos dots van. Por eso los dots cambian al cambiar el ancho. El listener de scroll sincroniza los dots cuando el usuario arrastra a mano.

Laboratorio 4

Explorador responsive

Lista las media queries reales y dice cuales estan activas en el ancho que elijas. Muestra el alto del header y los dos inputs de busqueda.

Aca se ve la trampa del proyecto. home.css y navbar.css cortan en min-width: 780px; footer.css usa min-width: 781px y max-width: 780px. A 781 px exactos el footer ya esta en escritorio y el navbar todavia en mobile.

Laboratorio 5

La formula clamp() del footer

Dibuja la curva real de cada clamp() de footer.css y te dice el valor que resulta en cada ancho.

Como se arman los numeros. Todos tienen la forma clamp(min, calc(MAX - (1920px - 100vw) * k), MAX). El k es una pendiente elegida a mano para que el valor llegue al minimo justo en el ancho de referencia. No hay variables CSS: cada linea recalcula.

Laboratorio 6

Botón de comentario: la maquina de estados

initCommentSubmit() real, con bitacora de eventos. Se ve el momento exacto en que el swap depende del animationend.

La clase enviado dura 1200 ms. El sobre es solo confirmacion. Si COMMENT_RESET_MS fuera menor que los 500 ms de la sacudida, el boton recien reiniciado volveria a sacudirse. Bajalo a 200 y mira que pasa.

Para antes de entregar

Pendientes y trampas

Lo que falta y lo que muerde si no lo tengo presente.

Falta hacer

  • Rama. El enunciado pide gh-pages y el repo esta en git-pages. pendiente
  • Carrito. carritoTotal sube con cada click y no hay logica de carrito. Es placeholder asumido, pero si lo preguntan, esta aclarado.
  • Precios y premium. La API no dice si un juego es gratis, asi que marcarPremium() lo simula con Math.random(). Cada carga marca cards distintas.
  • Login sin JS. No valida nada. Si la catedra lo pide, se agrega el mismo patron de CAMPOS.

Trampas del codigo

  • 780 contra 781. No es un error de redondeo: footer.css tiene min-width: 781px y max-width: 780px, mientras home.css y navbar.css cortan en 780. A 781 px el footer ya esta en escritorio y el navbar sigue en mobile.
  • Index.html con I mayuscula. En Windows no lo nota; en Linux o en GitHub Pages puede romper un link.
  • Los ids de las categorias no estan en el HTML. Los pone buildCategories(). Si se busca #cat- en el archivo estatico, no aparece.
  • El titulo del enunciado dice "las 3 paginas". Hay cuatro HTML porque login y registro estan separados, pero son dos de las tres (autenticacion).
  • El loading es de 5 s fijos. Si la API responde antes, el usuario igual espera. Es lo que pide el enunciado, no es un bug.
  • animationend se dispara por animacion, no por elemento. Por eso el boton de comentario filtra por animationName !== 'barridoEnviar': el boton tiene mas de una animacion.
  • Sin alt en las cards. Las cards del home son <a> con fondo y un <p>, sin alt: el nombre es el texto.

Para el parcial

Practica

Si te piden "modificá el código para que pase tal cosa", casi siempre es cambiar un número en una línea o una regla de CSS. Acá está el mapa de dónde está cada cosa, seis retos que se corrigen solos y un test de 24 preguntas.

El test no te dice la respuesta correcta. Al corregir sabrás si está bien o mal y nada más: la explicación y el enlace al código quedan detrás del botón Ver por qué, para que no se te coman las pistas de a gratis. El progreso se guarda en este navegador.

Cada reto trae el fragmento real del archivo. Lo editás, tocás Comprobar, y el veredicto se arma midiendo el resultado: los de CSS corren el pie real del sitio en un iframe y se lee el CSSOM. Si te dice "mal", no te dice cuál era el valor correcto: la explicación está detrás del botón.
